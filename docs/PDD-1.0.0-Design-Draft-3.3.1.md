# PDD 1.0.0 — 개발 설계 초안 3.3.1

## Physical Destruction and Deforming

**프로젝트:** Create Aeronautics 충돌 손상·변형 애드온  
**대상 환경:** Minecraft Java 1.21.1 · NeoForge 21.1.x · Create 6.x · Create Aeronautics 1.3.x · Sable 2.0.x  
**문서 버전:** 설계 초안 3.3.1  
**목표 릴리스:** PDD 1.0.0

---

## 1. 문서 목적

이 문서는 마인크래프트 모드 개발을 처음 접하는 사람도 PDD가 해결하려는 문제, 작동 방식, 주요 계산, 성능 원칙 및 구현 순서를 이해할 수 있도록 작성한 설계 보고서이다.

이 문서에서 **PDD 1.0.0은 목표 릴리스 버전**을 의미한다. 초안 3.3.1은 그 릴리스를 만들기 위한 설계 문서의 버전이다. 따라서 이 문서는 개발 버전 0.1.3의 작업 목록이나 0.1.2의 구현 상태 보고서가 아니다.

이 문서는 설계 방향을 설명한다. 실제 모드의 API 호출 위치, 인수의 좌표계와 단위, 이벤트가 발생하는 시점 등은 대상 버전의 소스와 실제 게임 테스트를 통해 확인해야 한다. 확인되지 않은 사항을 이미 구현된 기능처럼 취급하지 않는다.

## 2. PDD란 무엇인가?

PDD는 *Physical Destruction and Deforming*의 약자로, 물리적 파괴와 변형을 뜻한다.

Create Aeronautics에서 비행체나 다른 물리 구조물이 움직이다가 지면·벽·다른 구조물과 충돌하면, 충돌한 블록이 손상되거나 변형되고 충분한 충격에서는 파괴되도록 만드는 것이 PDD의 목적이다.

기본 마인크래프트에서는 블록이 일반적으로 고정된 격자 위치에 놓이며, 채굴·폭발 등 기존 게임 규칙에 따라 파괴된다. PDD는 여기에 **물리 충돌에 따른 블록 손상 시스템**을 추가한다.

예를 들어 비행체가 지면에 강하게 충돌하는 경우 다음과 같은 결과를 목표로 한다.

- 충돌한 블록에 손상이 누적된다.
- 블록의 재료 특성에 따라 같은 충격에도 손상량이 달라진다.
- 일부 블록은 파괴되기 전에 영구 변형될 수 있다.
- 충격의 일부가 주변 블록으로 전달되어 추가 손상이나 연쇄 파괴를 일으킬 수 있다.
- 충격이 충분히 크면 충돌한 구조물과 대상 블록 양쪽이 손상될 수 있다.

이 결과는 단순한 충돌 횟수가 아니라 상대 속도, 유효 질량, 충돌 방향, 블록 물성, 누적 손상 등을 바탕으로 결정한다.

## 3. 기존 모드와 PDD의 역할

| 구성 요소 | 역할 |
|---|---|
| Minecraft | 월드, 블록, 블록 상태, 아이템 드롭 및 기본 파괴 처리 제공 |
| Create | 기계·블록 기반 제작 시스템 제공 |
| Create Aeronautics | 움직이는 물리 구조물과 관련 기능 제공 |
| Sable | 물리 구조물의 움직임과 충돌 계산을 위한 기반 제공 |
| PDD | 충돌 결과를 블록 손상·변형·파괴 규칙으로 변환 |

PDD는 별도의 물리 엔진을 만들지 않는다. Sable과 Aeronautics가 담당하는 움직임과 기존 충돌 반응을 보존하고, 그 충돌이 마인크래프트 월드의 블록에 어떤 영향을 주어야 하는지를 계산한다.

**핵심 원칙:** 물리 계산과 게임 내 피해 계산은 연결하되, 같은 기능을 두 번 구현하지 않는다.

## 4. 전체 처리 과정

PDD의 기본 처리 흐름은 다음과 같다.

1. **충돌 정보 수집:** 기존 물리 시스템에서 충돌 관련 정보를 얻는다.
2. **정보 검증:** 충돌한 대상, 좌표, 방향, 속도 및 질량 정보를 확인한다.
3. **중복 제거:** 같은 충돌이 여러 경로로 전달되었는지 확인한다.
4. **충격 계산:** 상대 속도와 유효 질량을 바탕으로 충격 규모를 추정한다.
5. **에너지 배분:** 직접 손상, 변형, 물리 반응 및 주변 응력 전파에 사용할 몫을 정한다.
6. **물성 적용:** 경도·연성·탄성에 따라 블록의 반응을 계산한다.
7. **파괴 판정:** 누적 손상이 블록의 파괴 임계값에 도달했는지 확인한다.
8. **월드 변경 예약:** 파괴·변형·상태 갱신 작업을 처리 대기열에 등록한다.
9. **안전한 서버 처리:** 예약된 작업을 실행하고 저장·드롭·시각 효과를 갱신한다.

물리 충돌 콜백 안에서 월드 블록을 바로 변경하지 않는다. 계산 중인 물리 시스템과 월드 상태를 동시에 변경하면 충돌 처리나 기존 모드 동작이 손상될 수 있기 때문이다.

## 5. 블록의 세 가지 물성

PDD는 블록 종류별로 경도, 연성, 탄성을 관리한다. 이 값들은 서로 다른 역할을 담당한다.

### 5.1 경도 — 직접 충격 손상에 대한 저항

경도는 직접 충격으로 발생하는 손상량을 조절한다.

- 경도가 낮으면 같은 충격에서 더 많은 손상이 발생한다.
- 경도가 높으면 같은 충격에서 손상이 줄어든다.
- 경도가 높다고 해서 블록이 완전히 무적이 되는 것은 아니다.

경도는 **0~255** 범위로 저장한다. 경도와 파괴 임계값은 별개의 값이다. 경도는 충격으로 얼마나 손상되는지를 조절하고, 파괴 임계값은 누적 손상이 어느 수준에 도달해야 파괴되는지를 결정한다.

### 5.2 연성 — 파괴 전 영구 변형 허용량

연성은 블록이 파괴되기 전에 영구적으로 변형될 수 있는 정도를 조절한다.

연성이 높은 블록은 파괴 전에 더 많은 변형을 허용할 수 있고, 연성이 낮은 블록은 변형이 제한될 수 있다. 연성은 **0~100%** 범위로 저장한다.

**연성은 직접 손상량을 감소시키는 계수가 아니다.** 직접 손상과 영구 변형은 별도로 계산한다.

마인크래프트의 일반 블록은 임의의 소수 좌표로 자유롭게 휘어지는 물체가 아니다. 따라서 실제 구현에서는 블록을 어느 단위로 이동시킬지, 이동할 공간이 있는지, 이동이 불가능하면 파괴 판정을 어떻게 처리할지 규칙이 필요하다.

### 5.3 탄성 — 주변 블록으로 전달되는 응력 조절

탄성은 충격을 받은 블록에서 주변 블록으로 전달되는 PDD 응력의 양을 조절한다.

- 탄성이 높으면 주변으로 전달되는 응력이 감소한다.
- 탄성이 낮으면 더 많은 응력이 주변으로 전달될 수 있다.

탄성은 **0~100%** 범위로 저장한다. 이는 PDD가 정의하는 게임 규칙이며, Sable의 물리적 반발 계수와 같은 개념이 아니다.

### 5.4 물성 역할 요약

| 물성 | 결정하는 항목 | 직접 손상량 감소 |
|---|---|---|
| 경도 | 직접 충격 손상 저항 | 적용 |
| 연성 | 파괴 전 영구 변형 허용량 | 적용하지 않음 |
| 탄성 | 주변 블록으로 전달되는 PDD 응력 | 직접 손상과 별도 처리 |

## 6. 충돌 강도 계산

### 6.1 속도만으로 판단하지 않는다

같은 속도로 충돌하더라도 가벼운 물체와 무거운 구조물은 충격 규모가 다르다. 따라서 속도뿐 아니라 질량도 고려한다.

기본 운동에너지 식은 다음과 같다.

\[
E = \frac{1}{2}mv^2
\]

여기서 \(E\)는 운동에너지, \(m\)은 질량, \(v\)는 속도이다.

충돌에서는 서로 접근하는 방향의 상대 속도가 중요하다. 충돌면에 수직인 방향을 **법선 방향**이라고 한다. PDD는 정면으로 부딪히는 상황과 옆으로 스쳐 지나가는 상황을 구분하기 위해 법선 방향 상대 속도를 사용하도록 설계한다.

\[
v_n = \max(0,-\vec v_{rel}\cdot\hat n)
\]

- \(\vec v_{rel}\): 두 대상의 상대 속도
- \(\hat n\): 충돌면의 단위 법선 벡터
- \(v_n\): 서로 접근하는 방향의 상대 속도

회전하는 구조물은 접촉점의 회전 속도까지 고려해야 한다. Sable의 API에서 실제로 얻는 벡터와 실수 인수가 위 식의 어떤 값에 해당하는지는 호출 경로와 인수의 의미를 확인한 뒤 연결한다.

### 6.2 두 물체의 충돌

두 물체의 단순 병진 운동을 가정하면 환산 질량은 다음과 같다.

\[
\mu = \frac{m_A m_B}{m_A+m_B}
\]

\[
E_{impact}=\frac{1}{2}\mu v_n^2
\]

회전 관성까지 고려할 수 있다면 단순 환산 질량보다 접촉 방향의 유효 질량을 사용하는 것이 적절할 수 있다. Sable에는 질량과 관성 관련 정보를 제공하는 API가 있지만, 실제 접촉점과 법선 정보를 확보할 수 있는지는 별도로 검증해야 한다.

### 6.3 미세 접촉 필터

충돌 횟수만으로 피해를 결정하지 않는다. 잎과 반복해서 접촉했다는 이유만으로 고경도 블록이 파괴되어서는 안 된다. 반면 질량과 속도가 충분한 강한 충돌은 큰 피해를 발생시킬 수 있어야 한다.

따라서 최소 충돌 에너지와 필요시 최소 상대 속도를 설정한다. 구체적인 임계값은 실제 게임 테스트 후 정하며, 미확정 수치를 확정값처럼 취급하지 않는다.

## 7. 충격 에너지와 손상량의 관계

물리 에너지와 게임 내 손상 수치는 단위가 다르다. 충격 에너지를 곧바로 손상률로 사용하지 않고, 별도의 보정 함수로 변환한다.

경도는 0~255 범위이며 다음과 같이 정규화할 수 있다.

\[
h=\frac{H}{255}
\]

경도 255가 완전한 무적이 되는 것을 막기 위한 후보 손상 계수는 다음과 같다.

\[
f_H=f_{min}+(1-f_{min})(1-h)^\gamma
\]

\[
D_{raw}=F(E_{assigned})f_H
\]

- \(H\): 블록의 경도
- \(f_{min}\): 경도가 매우 높아도 남겨 둘 최소 피해 계수
- \(\gamma\): 경도 곡선의 형태를 조절하는 계수
- \(F\): 충격 에너지를 게임 내 손상량으로 변환하는 함수
- \(E_{assigned}\): 해당 블록에 실제 배분한 충격 에너지

이 수식은 설계 후보이다. 계수와 보정 함수는 테스트를 통해 결정하며, 아직 확정되지 않은 숫자를 임의로 넣지 않는다.

## 8. 누적 손상과 파괴 임계값

블록은 한 번의 충격으로 파괴되지 않더라도 여러 차례 충격을 받아 손상이 누적될 수 있다.

\[
D_{new}=\min(255,D_{old}+\Delta D)
\]

- \(D_{old}\): 기존 누적 손상
- \(\Delta D\): 이번 충격으로 추가된 손상
- \(D_{new}\): 충격 후 누적 손상

파괴는 누적 손상이 해당 블록의 파괴 임계값에 도달했을 때 판정한다. 파괴 임계값은 경도와 분리한다. 경도는 손상량을 조절하고, 파괴 임계값은 파괴 시점을 결정한다.

파괴 임계값을 계산하는 구체적인 함수는 추가 설계와 게임 테스트가 필요하다.

## 9. 충격 에너지의 중복 적용 방지

한 번의 충돌에서 발생한 에너지를 충돌한 모든 블록에 각각 전부 적용하면 실제 충격보다 훨씬 큰 피해가 발생할 수 있다.

따라서 충격 에너지를 직접 손상, 영구 변형, 물리 반응 및 주변 응력 전파에 분배한다.

\[
E_{impact}\approx E_{damage}+E_{deform}+E_{response}+E_{propagation}+E_{unresolved}
\]

이 식은 에너지 배분을 관리하기 위한 설계 모델이다. 각 항목의 정확한 계산법은 추가 검증이 필요하다. 게임 내 손상량 자체를 물리 에너지와 같은 단위로 더해서는 안 된다.

충돌한 구조물과 대상 블록은 각자의 물성 및 파괴 임계값에 따라 독립적으로 판정할 수 있지만, 같은 최초 충돌 에너지를 양쪽에 중복해서 전부 적용해서는 안 된다.

## 10. 주변 블록으로의 응력 전파

응력 전파는 최초 충돌의 영향이 주변 블록으로 전달되는 과정이다.

블록 \(i\)에서 블록 \(j\)로 전달되는 기여량은 다음 후보식으로 표현할 수 있다.

\[
q_{i\rightarrow j}=q_iw_{ij}(1-e_i)
\]

- \(q_i\): 블록 \(i\)에 남아 있는 전파 예산
- \(w_{ij}\): 두 블록 사이의 전달 가중치
- \(e_i\): 블록 \(i\)의 탄성(0~1)
- \(q_{i\rightarrow j}\): 이웃 블록에 전달할 응력 기여량

여러 경로에서 같은 블록에 응력이 도달하면 기여량을 합산한다.

\[
Q_j=\sum_i q_{i\rightarrow j}
\]

합산만으로 에너지 보존이 보장되는 것은 아니므로 다음 제한을 함께 적용한다.

- 최대 전파 깊이
- 최대 방문 블록 수
- 최소 전파 기여량
- 충돌 전체의 전파 예산
- 블록별 기여량 상한
- 같은 충돌의 반복 처리 방지

기여량을 합산한 뒤 블록별 손상을 한 번 계산하고, 파괴 임계값을 판정한다.

## 11. 고속 이동과 블록 관통 방지

물체가 한 번의 게임 틱 사이에 먼 거리를 이동하면, 충돌 검사에서 중간 블록을 놓칠 수 있다. 이를 터널링 또는 충돌 누락이라고 한다.

PDD는 Sable의 충돌 검사를 대체하지 않고, 필요한 경우 이동 경로를 추가 검사하는 보완 방식을 검토한다.

1. 이전 위치와 예측 위치를 확인한다.
2. 구조물의 크기를 고려해 충돌 후보 블록을 찾는다.
3. 후보 블록의 실제 충돌 모양을 검사한다.
4. 최초 충돌 위치를 계산한다.
5. 기존 물리 충돌 처리와 연결한다.
6. PDD 피해 이벤트를 생성한다.

계단이나 반 블록처럼 블록마다 충돌 모양이 다를 수 있으므로 모든 블록을 단순한 정육면체로 가정하지 않는다. 이미 Sable이 처리한 충돌을 PDD가 다시 발생시키지 않도록 해야 한다.

초기 구현은 움직이는 물리 구조물과 고정 월드 블록 사이의 이동을 우선 대상으로 한다. 회전 구조물은 접촉점과 방향이 변하므로 별도 검증 후 확장한다.

계산 한도를 초과했다고 충돌 검사를 생략하고 구조물을 그대로 통과시키면 안 된다. 안전한 이동 제한이나 검증된 대체 경로가 필요하다.

## 12. 물성 자동 등록과 캐시

### 12.1 블록마다 반복 계산하지 않는다

월드에 같은 종류의 블록이 많이 설치되어 있더라도, 경도·연성·탄성은 일반적으로 블록 종류의 공통 물성으로 관리할 수 있다. 설치된 블록 하나하나마다 제작법을 분석하면 같은 계산이 반복된다.

따라서 PDD는 초기화 단계에서 등록된 블록 종류를 탐색하고, 종류별 물성을 미리 계산해 캐시에 저장한다.

### 12.2 등록 과정

1. Minecraft/NeoForge의 블록 등록 체계를 통해 등록된 블록 종류를 수집한다.
2. 블록 등록 ID를 기준으로 각 종류를 식별한다.
3. 기본 블록 속성과 가능한 재료 정보를 분석한다.
4. 제작법은 물성 추론을 위한 보조 정보로 활용한다.
5. 추론할 수 없는 블록에는 기본값을 적용한다.
6. 사용자 지정 물성은 자동 추론값보다 우선한다.
7. 계산 결과를 블록 종류별 물성 테이블에 저장한다.

Java 클래스 파일 전체를 무차별적으로 탐색하는 방식은 기본안으로 사용하지 않는다. 실제 등록된 블록 종류와 등록 ID를 기준으로 처리한다.

### 12.3 제작법과 물성의 한계

제작법만으로 모든 블록의 물성을 정확하게 알 수 있는 것은 아니다. 제작법은 추론에 활용할 수 있는 정보 중 하나다. 재료가 혼합되거나 제작법이 없는 블록에는 별도의 추론 규칙이나 기본값이 필요하다.

제작법이 데이터팩 재로딩 등으로 변경되면 관련 캐시를 갱신한다. 갱신 중에는 이전 값과 새 값이 혼용되지 않도록 한다.

### 12.4 종류별 데이터와 좌표별 데이터

| 데이터 | 저장 단위 |
|---|---|
| 경도 | 블록 종류별 공통 데이터 |
| 연성 | 블록 종류별 공통 데이터 |
| 탄성 | 블록 종류별 공통 데이터 |
| 누적 손상 | 실제로 손상된 블록 좌표 |
| 누적 변형 | 실제로 변형된 블록 좌표 |
| 균열 표시 강도 | 표시가 필요한 블록 |

손상되지 않은 블록에는 개별 손상 상태 객체를 만들지 않는다.

## 13. 메모리 저장 규칙

블록 상태 수치는 다음 범위를 사용한다.

| 수치 | 범위 | 저장 폭 |
|---|---:|---:|
| 경도 | 0~255 | 1바이트 |
| 누적 손상 | 0~255 | 1바이트 |
| 누적 변형 | 0~255 | 1바이트 |
| 균열 표시 강도 | 0~255 | 1바이트 |
| 연성 | 0~100 | 1바이트 |
| 탄성 | 0~100 | 1바이트 |

1바이트라는 조건은 각 수치의 저장 폭을 의미한다. 상태 전체가 1바이트라는 뜻은 아니다.

Java의 `byte`는 부호가 있는 자료형이므로 128~255 값을 처리할 때 부호 확장에 주의한다. 계산은 `int` 또는 `double`로 수행하고, 저장할 때 허용 범위를 검증한다.

PDD는 손상 상태를 가진 블록만 저장하는 희소 저장 방식을 사용한다. 실제 월드 저장·로드 연동과 블록 이동 시 상태 처리 규칙은 구현 단계에서 검증해야 한다.

## 14. 폭발과 투사체

### 14.1 폭발

PDD는 Minecraft의 일반 블록 폭발 처리와 Aeronautics의 물리 구조물 폭발 처리를 무조건 대체하지 않는다. 기존 동작을 보존하면서 폭발로 파괴되지 않은 주변 블록에 추가 손상을 적용하는 방식을 목표로 한다.

같은 블록에 기존 폭발 처리와 PDD 피해가 중복 적용되거나 아이템이 두 번 드롭되지 않도록 해야 한다. 폭발 거리, 차폐, 강도 및 블록 물성을 반영하는 보정 모델이 필요하다.

### 14.2 투사체

화살이나 Create 대포 투사체가 충돌하면 가능한 경우 실제 물리 정보를 우선 사용한다. 물리 데이터가 없는 경우 기존 게임의 피해량을 대체 입력으로 활용할 수 있다.

게임 내 엔티티 피해량은 물리적 충돌 에너지와 동일하지 않으므로 별도의 보정 규칙이 필요하다. 투사체가 충돌 직후 제거되더라도 동일 사건의 피해가 여러 번 생성되지 않도록 한다.

## 15. 균열 시각화

실제 손상 상태와 화면에 표시되는 균열 상태는 별도 데이터다.

- **실제 손상:** 파괴 판정에 사용한다.
- **균열 표시 강도:** 플레이어가 손상 정도를 볼 수 있도록 한다.
- **시각 효과 회복:** 시간이 지나며 표시를 줄일 수 있다.

균열 표시가 사라져도 실제 손상이 자동으로 복구되는 것은 아니다. Minecraft의 기존 균열 텍스처를 활용하는 방식을 우선 검토하고, 월드 전체를 매 틱 탐색하지 않고 표시가 필요한 블록만 갱신한다.

## 16. 파괴·변형과 월드 변경 큐

물리 충돌 콜백에서는 블록을 직접 파괴하거나 이동하지 않는다. 충돌 콜백은 검증된 이벤트를 만들고, 실제 월드 변경은 안전한 서버 처리 단계에서 실행한다.

작업 큐에는 다음과 같은 작업이 들어갈 수 있다.

- 손상 상태 갱신
- 파괴 임계값 판정
- 블록 파괴와 아이템 드롭
- 영구 변형
- 균열 표시 갱신
- 필요한 클라이언트 동기화

블록을 파괴하거나 이동하기로 예약하면 해당 좌표를 예약 상태로 기록해 중복 변경을 막는다. 한 틱에 처리할 수 있는 작업 수에는 상한을 둔다. 한도를 넘은 작업은 우선순위에 따라 이월하며, 이미 승인된 파괴 작업을 조용히 폐기하지 않는다.

블록 엔티티가 가진 추가 데이터와 기존 드롭 규칙을 보존해야 한다. 실제 월드 저장·로드, 클라이언트 표시 동기화 및 서버 종료 시 대기 작업 처리 방식은 구현 단계에서 검증한다.

## 17. 성능 최적화 원칙

PDD는 다음 원칙으로 불필요한 연산을 줄인다.

1. 물성은 블록 종류별로 미리 계산한다.
2. 충돌 처리 중 제작법을 반복 분석하지 않는다.
3. 동일 충돌 이벤트를 중복 계산하지 않는다.
4. 손상되지 않은 블록에는 개별 상태 객체를 만들지 않는다.
5. 주변 블록 탐색에 깊이와 방문 수 제한을 둔다.
6. 실제 표시가 필요한 균열만 갱신한다.
7. 전체 월드 대신 충돌 주변의 후보 블록을 검사한다.
8. 작업 큐 한도를 두되 승인된 작업을 폐기하지 않는다.
9. 불필요한 임시 객체 생성을 줄인다.
10. 실제 측정 전에는 특정 TPS나 메모리 절감률을 보장하지 않는다.

## 19. 검증 및 시험 계획

### 19.1 API 및 충돌 수집

- 실제 충돌 콜백 인수의 의미와 좌표계를 확인한다.
- 구조물과 일반 월드 블록 사이의 충돌을 수집할 수 있는지 확인한다.
- 구조물끼리의 충돌을 수집할 수 있는지 확인한다.
- Aeronautics와 Sable의 기존 충돌 반응이 유지되는지 확인한다.
- 동일 충돌 이벤트가 중복 처리되지 않는지 확인한다.

### 19.2 피해 계산

- 경도 0과 255의 결과를 비교한다.
- 연성을 바꿔도 직접 손상량이 변하지 않는지 확인한다.
- 탄성이 주변 응력 전달량을 조절하는지 확인한다.
- 경도와 파괴 임계값이 독립적으로 작동하는지 확인한다.
- 반복적인 미세 접촉으로 고경도 블록이 부당하게 파괴되지 않는지 확인한다.

### 19.3 에너지 분배와 연쇄 파괴

- 구조물 양쪽에 피해를 적용할 때 충격 에너지가 중복되지 않는지 확인한다.
- 여러 경로에서 도달한 기여량이 합산되는지 확인한다.
- 전파 깊이와 방문 블록 수 제한이 적용되는지 확인한다.
- 4블록 낙하 등 일반적인 충돌에서 구조물 전체가 비현실적으로 파괴되지 않는지 확인한다.

### 19.4 저장·성능

- 손상 상태가 저장·로드 후 유지되는지 확인한다.
- 파괴된 블록의 손상 상태가 정리되는지 확인한다.
- Java `byte`의 부호 문제로 값이 잘못 변환되지 않는지 확인한다.
- 손상되지 않은 블록에 상태 객체가 생성되지 않는지 확인한다.
- 큐 한도를 넘은 작업이 안전하게 이월되는지 확인한다.
- 대규모 충돌에서 TPS와 메모리 사용량을 측정한다.

### 19.5 폭발·투사체

- 기존 폭발 처리와 PDD 추가 피해가 중복되지 않는지 확인한다.
- 아이템 드롭이 중복되지 않는지 확인한다.
- 물리 데이터가 없는 투사체의 대체 모델을 검증한다.
- 고속 투사체가 블록을 관통하는지 확인한다.

## 20. 설계상 확정 사항과 추가 검증 항목

### 20.1 설계상 확정 사항

- PDD는 Sable의 물리 계산을 대체하지 않는다.
- 경도는 직접 충격 손상량을 조절한다.
- 연성은 직접 손상 감소가 아니라 파괴 전 변형 허용량에 영향을 준다.
- 탄성은 주변 블록으로 전달되는 PDD 응력을 조절한다.
- 파괴 임계값은 경도와 분리한다.
- 물성은 블록 종류별로 초기 등록하고 캐시한다.
- 충돌 처리 중 제작법을 반복 분석하지 않는다.
- 손상 상태는 실제로 손상된 블록만 저장한다.
- 물리 콜백에서 월드 블록을 직접 변경하지 않는다.
- 한 충돌의 에너지를 여러 블록에 중복 배분하지 않는다.
- 기존 Sable/Aeronautics 충돌 반응과 Minecraft의 파괴 규칙을 보존한다.

### 20.2 추가 검증이 필요한 사항

- 실제 충돌 콜백의 인수 의미, 단위, 좌표계 및 호출 시점
- 상대 속도·법선·접촉점 정보를 얻는 정확한 API 경로
- 회전 관성을 반영한 유효 질량 계산의 적용 가능성
- 일반 월드 블록의 충돌을 수집할 지점
- 충돌 에너지를 게임 내 손상량으로 변환하는 보정 함수
- 직접 손상·변형·응력 전파 사이의 에너지 배분 규칙
- 블록 이동 실패 시 파괴와 변형 중 어느 처리를 우선할지
- 전파 예산과 작업 큐의 구체적인 수치
- 월드 저장·로드와 클라이언트 균열 표시 동기화 방식

검증되지 않은 항목은 이미 해결된 기능처럼 취급하지 않는다. 구현을 막는 API 가정은 소스 추적과 실제 게임 테스트로 해결한 뒤 진행한다.

## 21. 최종 목표

PDD 1.0.0의 목표는 Create Aeronautics의 물리 구조물에 충돌 손상, 영구 변형, 연쇄 파괴를 안정적으로 추가하는 것이다.

완성된 시스템은 충돌을 감지하는 데서 끝나지 않는다. 충격의 규모를 계산하고, 블록별 물성을 적용하며, 손상을 누적하고, 주변 블록으로 전달되는 응력을 제한하고, 최종 결과를 마인크래프트 월드에 안전하게 반영해야 한다.

이를 위해 개발은 다음 순서를 따른다.

**실제 API 연동 경로 검증 → 충돌 정보 수집 → 물성 자동 등록 → 직접 손상 계산 → 충격 예산과 응력 전파 → 월드 변경 큐 → 저장·시각화 → 폭발·투사체·고속 충돌 확장**

이 순서는 구현 편의만을 위한 것이 아니다. 기초 연동이 검증되지 않은 상태에서 파괴 기능을 먼저 구현하면, 잘못된 충돌 정보나 중복 이벤트 때문에 피해 계산 전체를 다시 설계해야 할 수 있기 때문이다.

PDD 1.0.0은 단순한 블록 파괴 효과가 아니라, 검증 가능한 충돌 데이터와 일관된 피해 규칙을 기반으로 동작하는 Create Aeronautics용 물리 손상 애드온을 목표로 한다.
