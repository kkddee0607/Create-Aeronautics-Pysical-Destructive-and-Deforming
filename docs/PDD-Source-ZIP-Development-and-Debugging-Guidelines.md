# PDD 소스 ZIP 개발·디버깅 운영 지침

**문서 분류:** 개발 작업 지침 / 모바일 환경 최적화 / 재발 방지 체크리스트  
**적용 대상:** PDD(Physical Destruction and Deforming) 모든 후속 버전의 소스 ZIP, 디버그 빌드, GitHub Apply 및 테스트  
**개정 기준:** 2026-10-27 / PDD 0.2.1-debug의 관측 기본 OFF 및 일반 블록 충돌 수집 경로 누락 문제  
**대상 환경:** Minecraft Java 1.21.1 · NeoForge 21.1.x · Create 6.x · Create Aeronautics 1.3.x · Sable 2.0.x  
**개발자의 작업 환경:** 모바일 기기 중심. 로컬 PC IDE·터미널·게임 실행·JAR 빌드가 항상 가능하다고 가정하지 않는다.

> **최우선 원칙:** 개발자가 명시한 *이번 빌드의 핵심 목적*은 기본 활성화된 상태로 제공한다. 오류·성능·호환성 위험은 숨기거나 임의로 기능을 끄는 이유가 아니라, 관측·검증·보고해야 할 대상이다. 단, 요청 범위를 벗어난 파괴·월드 변경 같은 별도의 위험 기능까지 자동 활성화한다는 뜻은 아니다.

## 1. 문제 발생 경위와 재발 방지 기준

### 1.1 PDD 0.2.1-debug 실패 사례

이번 빌드의 목적은 **Sable 충돌 콜백이 실제 게임 중 호출되는지 로그로 확인**하는 것이었다. 그러나 제공된 소스에 다음 문제가 있었다.

1. `SableContactQueue.ENABLED`를 `Boolean.getBoolean("pdd.debugCollisions")`로 선언하여 JVM 옵션 미설정 시 관측 기능이 꺼졌다.
2. `pdd.mixins.json`의 `required: false`, `injectors.defaultRequire: 0`으로 Mixin 주입 실패가 치명적 오류로 드러나지 않을 수 있었다. **이 값들이 Mixin 자체를 비활성화한다는 뜻은 아니다.**
3. `SableCollisionBridgeMixin`에서 `ENABLED`가 거짓이면 콜백 데이터를 수집하지 않았다.
4. `PhysicalDestroyDeform.onServerTick`에서도 디버그 플래그가 거짓이면 큐 처리와 로그 출력을 건너뛰었다.
5. 관측 대상이 Sable의 일부 기존 콜백 구현체로 제한되어 있어 일반 블록 충돌까지 관측되는 것은 아니었다.
6. 핵심 기능을 사용하려면 모바일 사용자가 JVM 옵션을 별도로 입력하거나 소스를 수정하고 다시 빌드해야 했다.

**판정:** 1번은 핵심 관측 기능의 기본 비활성화, 5번은 **Sable → PDD 충돌 데이터 전달 검증이라는 핵심 목적에 필요한 공통 충돌 경로 누락**이다. 둘 다 핵심 요구사항 불이행이다. 2번은 별도의 주입 실패 진단 정책 문제다.

### 1.2 변경 불가 원칙

- 사용자가 `충돌 콜백 확인 버전`을 요구했다면 **콜백 관측·충돌 로그를 기본 ON**으로 만든다.
- 사용자가 `파괴·변형 구현`을 요구했다면 해당 기능을 임의로 생략한 뒤 구현한 것처럼 설명하지 않는다. 미확정 조건은 명시하고 근거·구현 방법·검증 계획을 제시한다.
- 특정 단계의 실험에서 월드 변경을 명시적으로 제외했다면 **관측 ON / 월드 변경 OFF**로 분리한다.
- 실패를 회피하기 위해 이벤트 등록, Mixin 주입, 로깅, 데이터 수집 등을 조용히 건너뛰는 설계는 금지한다.
- 안정성을 위해 제한이 필요하면 **기능을 끄는 대신** 큐 용량, 처리 시간 예산, 로그 샘플링 및 누락 카운터를 사용한다. 이 제한으로 관측 불가능한 경우가 생긴다면 그 범위를 명시한다.
- 명시된 핵심 기능을 완전히 충족할 수 없으면 **부분 구현의 범위와 미달 항목을 버전 표시·문서·로그에 공개**한다. 성공했다고 주장하지 않는다.

## 1.3 추가 사고 분석: 충돌 데이터 전달 경로 자체의 누락

**검증 목적과 구현 대상의 일치가 최우선이다.** 0.2.1은 단순히 `FragileBlockCallback` 같은 특정 구현체가 호출되는지 확인하는 버전이 아니라, **Sable 물리 충돌 → PDD 수집 → 서버 측 관측 로그**가 실제 게임에서 성립하는지 확인하는 버전이다. 특정 블록 전용 콜백만 계측하고 일반 블록 충돌 경로를 빠뜨리면, 로그가 기본 ON이어도 테스트 목적을 달성하지 못한다.

- **확인된 당시 구현 범위:** `SableCollisionBridgeMixin`은 `FragileBlockCallback`과 `BeltBlockCallback`에만 주입하도록 작성되었다. 이 구현만으로 일반 블록·콜백 미지정 블록·물리 구조물 간 일반 충돌을 수집한다고 볼 수 없다.
- **반드시 조사할 경로:** Sable의 충돌 탐지 진입점 → 충돌 후보 생성 → 접촉/충돌 판정 → 블록별 콜백 선택(없을 때의 경로 포함) → 물리 응답 적용 → PDD 계측 지점. 실제 Sable 2.0.6 바이너리와 Aeronautics 연동 경로를 역분석해 근거를 남긴다.
- **금지:** `BlockSubLevelCollisionCallback`의 존재만으로 모든 충돌에 해당 콜백이 호출된다고 가정하기, `null` 콜백 경로를 무시하기, 특정 콜백 로그 한 건만으로 Sable → PDD 전체 연동 성공을 선언하기.
- **구현 원칙:** 모든 필수 충돌 사례가 지나가는 **공통 경로**를 우선 계측한다. 경로가 하나가 아니라면 각각 계측하고 중복 이벤트를 식별한다. Sable의 원래 반환값·운동량·충돌 반응을 변경하지 않는다.
- **검증 증거:** 실제 일반 블록 충돌의 이벤트 수집, PDD 큐 유입, 서버 로그 도달을 동일한 테스트 시나리오로 확인한다. 각 단계의 카운터를 구분해 기록한다. 단순 초기화 로그나 인공 이벤트는 연동 성공의 증거가 아니다.
- **미확정 사항:** 정확한 공통 메서드, 스레드, 좌표계, 접촉 데이터 형식은 소스/JAR 역분석 및 런타임 검증 전까지 확정하지 않는다. 미확정이면 개발 중 차단 항목으로 추적한다.

### 1.4 핵심 기능 누락 방지: 목적 역추적 검증

개발 시작 전 **사용자의 목적 → 필수 게임 상황 → 실제 엔진 호출 경로 → 주입/수집 코드 → 로그 증거**를 한 줄씩 연결한 *목적-경로 추적표*를 작성한다. 각 행에 실제 소스 파일·메서드·증거 또는 미확정 사유가 없으면 구현 착수 전 조사 대상으로 남긴다. 핵심 행이 비어 있으면 ZIP을 완성본으로 배포하지 않는다.

| 목적 | 필수 사례 | 확인할 경로 | 합격 증거 |
|---|---|---|---|
| Sable → PDD 전달 | 일반 블록으로 구성된 물리 구조물과 지형 충돌 | 콜백이 없더라도 실행되는 충돌 처리 경로 | 실제 충돌 이벤트가 PDD 큐 및 로그에 도달 |
| Sable → PDD 전달 | 물리 구조물끼리 충돌 | Aeronautics/Sable 구조물-구조물 접촉 경로 | 양쪽 구조물 식별과 접촉 데이터 또는 제한 사항 확인 |
| 기존 콜백과 공존 | 취약 블록/벨트 등 전용 콜백 | 전용 콜백 및 공통 경로 간 관계 | 원래 충돌 결과 유지, 중복 집계 여부 확인 |
| 실패 진단 | 충돌은 발생하지만 로그 없음 | 계측 → 큐 → 서버 틱 → 로그의 각 단계 | 미호출·미주입·드롭·비활성 구분 |

표의 사례는 **검증 목표**이며, 현재 구현 완료나 API 경로 확정을 의미하지 않는다.

## 2. 소스 개발을 시작하기 전 확인 순서

1. **최신 설계 문서 확인:** PDD 설계 채팅의 최신 확정 초안을 우선한다. 현재 보유 자료 중 기준 설계는 *설계 초안 3.3.1*이며, 이후 확정된 설계가 존재하면 그 문서가 우선한다.
2. **최신 구현 기준 확인:** GitHub 기본 브랜치의 최신 커밋, 가장 최근에 적용된 개발 소스, 관련 브랜치·PR을 확인한다. 이전 ZIP이나 대화 요약만을 최신 코드로 간주하지 않는다.
3. **개발 범위 확인:** 사용자가 지정한 버전, GitHub 이슈 번호, 목적, 완료 조건을 매핑한다. 이슈가 있으면 각각의 완료 근거를 남긴다.
4. **실제 의존성 확인:** 업로드된 Sable·Create·Aeronautics JAR의 정확한 버전과 메서드 시그니처를 기준으로 개발한다. 다른 버전의 예제 코드를 검증 없이 사용하지 않는다.
5. **기존 워크플로 확인:** `.github/workflows/`의 실제 Apply/Build 절차, ZIP 추출 규칙, 덮어쓰기 규칙, Gradle 실행 명령, 산출물 경로를 확인한다.
6. **불확실성 처리:** API가 확정되지 않았다면 소스/JAR 역분석, 제한된 진단 코드, 실패를 명확히 알리는 로깅으로 해결을 시도한다. 위험하다는 이유만으로 요구 기능을 제거하지 않는다.

**우선순위:** 사용자 명시 요구사항 → 최신 확정 설계 → 해당 버전의 실제 API·바이너리 증거 → 최신 프로젝트 구현 → 이전 버전 참고 코드. 충돌하는 근거가 있으면 무엇이 충돌하는지 기록한다.

## 3. 매 버전마다 작성하는 기능 계약

코딩 전에 다음 표를 채운다. 기본값을 `OFF`로 설정하려면 **사용자 요청 또는 단계별 설계상 명확한 근거**가 있어야 한다.

| 항목 | 필수 기록 사항 |
|---|---|
| 버전/기준 | 개발 버전, GitHub 기준 커밋, 설계 문서 버전 |
| 이번 빌드의 주목적 | 실제 게임에서 증명할 행동 1~3개 |
| 필수 활성 기능 | 기본값 ON인 콜백·로깅·기능과 그 진입 경로 |
| 단계상 비대상 기능 | 이번 단계에서 의도적으로 미구현/비활성화할 기능과 근거 |
| 이슈별 합격 조건 | Issue 번호 → 코드 파일 → 테스트 증거 |
| 관측 성공 조건 | 실제 로그 태그, 예상 발생 시점, 테스트 대상 |
| 실패 식별 조건 | 미주입·미호출·로그 제한·설정 비활성의 구별 방법 |
| 작업 환경 | 모바일만으로 GitHub 웹 UI에서 수행 가능한 단계 |

**예: 충돌 콜백 로그 테스트**

- `collisionObservation = ON`이 기본값이다.
- 게임 시작 시 활성 상태와 주입 대상 및 관측 범위를 출력한다.
- 실제 충돌이 발생하면 충돌 샘플 또는 명확한 집계 카운터가 증가한다.
- 일반 블록 충돌을 포함한 필수 관측 범위를 실제 수집 경로로 구현하고 검증한다. 미구현이면 테스트 버전을 완성으로 판정하지 않는다.
- 손상 적용/월드 변경은 별도 단계의 요구사항이 없으면 수행하지 않는다.

## 4. 디버그 버전의 활성화·로깅 규칙

### 4.1 기본 ON, 선택적 OFF

로그 시험 목적의 소스는 JVM 인수가 없어도 실행 가능해야 한다. 옵션은 **진입 조건이 아니라 예외적 비활성화 또는 로그 상세도 조절 수단**으로 사용한다.

```java
public static final boolean ENABLED = Boolean.parseBoolean(
    System.getProperty("pdd.debugCollisions", "true")
);
```

`Boolean.getBoolean("pdd.debugCollisions")`는 시스템 속성이 없으면 `false`를 반환하므로, 기본 ON 요구가 있는 디버그 버전에 사용하지 않는다.

단, 실제 현장에서는 `true`를 기본값으로 하더라도 해당 관측 코드가 JVM 시작 전에 로드되는지, 변경된 설정이 로그에 표시되는지 확인해야 한다. `-Dpdd.debugCollisions=false`는 선택적 OFF로 지원해도 된다.

### 4.2 활성 조건의 전 경로 검사

**설정 한 군데만 수정하면 끝난다고 가정하지 않는다.** 다음 전 경로에서 동일한 기능이 차단되지 않는지 검사한다.

1. Gradle 빌드 및 리소스 패키징 →
2. `neoforge.mods.toml`의 Mixin 설정 등록 →
3. `pdd.mixins.json` 로드 및 주입 →
4. 콜백 메서드 실제 호출 →
5. `SableCollisionBridgeMixin`의 수집 조건 →
6. `SableContactQueue`의 수용·카운터 →
7. `PhysicalDestroyDeform`의 서버 틱 소비 조건 →
8. 로그 출력 레벨/태그 →
9. `latest.log`에서 확인.

어느 단계에서든 `return`, 조건문, 예외 무시, 이벤트 미등록, 로거 비활성화가 있으면 **기능 계약과 대조**한다.

### 4.3 실패를 보이게 만드는 진단

- 시작 로그: 버전, 활성 설정, 콜백 계측 대상, 관측 범위, 해당 빌드의 비활성 게임플레이 기능을 표시한다.
- 계측 로그: 실제 Sable 콜백에서 획득한 값과 인공 테스트 값을 **다른 태그**로 구분한다.
- 정기 집계: 수집 총량, 처리량, 큐 overflow, 출력 생략량, 마지막 콜백 발생 시점(수집 가능할 때)을 표시한다.
- 종료 전/테스트 종료 시: 관측 대상 충돌을 발생시켰지만 콜백이 0건이라면 `NO_CALLBACK_OBSERVED` 등 진단 메시지를 남길 수 있도록 설계한다. 단, 콜백 대상 충돌 발생 자체가 확인되지 않았으면 원인을 단정하지 않는다.
- `Mixin required` / `defaultRequire`는 **주입 실패 정책**이다. `false` 및 `0`을 로그 비활성화와 혼동하지 않는다. 로그 테스트 전용 빌드에서는 필수 주입 실패를 빌드/기동 단계에서 명백히 알리도록 구성하는 방안을 우선 검토한다. 대상 버전과 Mixin 호환성을 먼저 확인하고, 오류 발생 위험을 명시한다.
- 로그를 제한하더라도 **관측 횟수 자체**는 보존하거나 누락 수를 집계한다. `최대 8건 출력`은 `최대 8건 관측`과 달라야 한다.

### 4.4 관측 기능과 게임플레이 기능은 분리

충돌 콜백의 원래 반환값·Sable 물리 반응은 변경하지 않는다. 충돌 관측과 실제 블록 파괴, 에너지 환산, 물리 시스템 갱신은 서로 다른 기능 단계다. **관측 목적 빌드에서 미검증 월드 변경을 끄는 것은 타당할 수 있지만, 관측까지 끄는 것은 타당하지 않다.**

## 5. 빠른 개발을 위한 검증 단계

| 단계 | 검증 항목 | 실패하면 |
|---|---|---|
| A. 정적 검사 | 요구사항·설정값·주입 대상·이슈 매핑·소스 누락 확인 | ZIP 생성 전 수정 |
| B. API 검사 | 업로드 JAR의 클래스·메서드·필드·버전 비교 | 호출 경로 수정, 미확정 사항 표기 |
| C. 소스 검사 | 가능한 범위의 Java 컴파일·단위 테스트·순수 모델 테스트 | 관련 코드 수정 |
| D. GitHub 빌드 | Actions의 Gradle 테스트/빌드 및 JAR 산출 검증 | 첫 오류 로그 기준 수정 ZIP 제작 |
| E. 게임 기동 | NeoForge 모드 로딩, Mixin 주입, 초기화 로그 검증 | 기동 실패와 계측 실패 구분 |
| F. 실제 기능 | 실충돌로 콜백 호출·데이터·반환값·범위 확인 | 커버리지·좌표계·호출 타이밍 재검토 |

- **A~C 통과는 D~F 통과를 의미하지 않는다.** 단위 테스트 성공을 실게임 충돌 성공이라고 보고하지 않는다.
- 처음 발견한 컴파일 오류를 고치는 과정에서 아직 확인하지 않은 오류가 존재할 수 있다. 로그 전문을 기준으로 관련 오류를 묶어 수정한다.
- 반복 빌드 비용을 줄이기 위해 사전에 일괄 검증하되, 실제 실행하지 않은 테스트를 실행했다고 주장하지 않는다.
- 디버깅을 위해 필요한 기능을 실패 가능성만으로 제거하는 대신, 실패 원인을 식별할 수 있는 경로를 추가한다.

### 5.1 버전별 즉시 확인할 테스트

- **로딩:** PDD가 로드되었는가? `INIT`, 의존성 버전이 출력되는가?
- **Mixin:** 관측 대상 주입이 실제 적용되었는가? 실패가 명확히 표시되는가?
- **호출:** 해당 콜백을 보유한 블록에 충돌했을 때 수집량이 증가하는가?
- **범위:** 일반 블록 충돌과 기존 콜백 대상 충돌을 구분하는가?
- **원본 보존:** Sable의 기존 반환값과 동작을 변경하지 않았는가?
- **고부하:** 지속 접촉·다수 충돌에서 메모리·로그 큐가 무한 증가하지 않는가?
- **근거:** 실제 로그와 인공 SELFTEST 출력이 구분되는가?

## 6. 모바일 전용 개발자에게 적합한 GitHub 작업 흐름

**원칙:** 모바일 브라우저의 GitHub 웹 UI만으로 ZIP 업로드 → 적용 → 빌드 → 로그 다운로드 → 오류 보고가 가능해야 한다. Git CLI, 로컬 Java/Gradle, 압축 해제 후 파일별 수동 업로드를 필수 조건으로 만들지 않는다.

### 6.1 소스 ZIP 전달 규칙

1. 파일 하나로 제공한다. 예: `PDD-0.2.2-debug-Apply-Source.zip`.
2. ZIP 내부 구조는 **현재 GitHub Apply Action이 요구하는 실제 경로 규칙**에 맞춘다. 루트 폴더를 유지할지 제거할지는 워크플로 코드에서 확인한다.
3. `src/`, Gradle 관련 설정 파일, 필요한 `resources/`, 테스트, 문서 및 예제 설정을 누락 없이 포함한다.
4. GitHub에 이미 있는 `.github/` 워크플로와 wrapper가 유지되어야 한다면 덮어쓰거나 삭제하지 않는다. 변경이 필수라면 이유와 영향부터 명시한다.
5. 불필요한 `.git/`, 빌드 캐시, 임시 출력, 중복 JAR, 개발 PC 절대 경로를 넣지 않는다.
6. ZIP 생성 후 파일 목록과 무결성을 검사한다. 실제 Apply 대상 파일이 모두 ZIP 안에 들어 있는지 확인한다.
7. 사용자가 **이미 빌드된 JAR**와 **빌드용 소스 ZIP**을 혼동하지 않도록 결과물의 종류를 이름과 설명에 표시한다.

### 6.2 GitHub 웹 UI 기준 실행 절차

실제 워크플로의 이름·동작은 해당 시점의 저장소에서 먼저 확인해야 한다. 0.2.1 당시 확인된 흐름은 아래와 같았다.

1. 모바일 GitHub에서 저장소의 `incoming/`으로 소스 ZIP을 업로드한다.
2. `Actions`에서 **Apply PDD ZIP** 실행 결과가 성공인지 확인한다. 이 단계는 소스 반영이지 JAR 빌드가 아니다.
3. 반영 커밋과 변경 파일을 확인한다.
4. `Actions`에서 **PDD Manual Build**를 실행하고 Gradle 작업 결과를 확인한다.
5. 빌드 성공 시 Actions의 **Artifacts**에서 실제 JAR을 받는다. 표시 이름이 구버전(`PDD-0.2.0-debug` 등)이라면 실제 JAR 파일 버전을 별도로 확인한다.
6. 게임을 실행할 수 있는 환경에서 JAR을 테스트한 뒤 `latest.log` 또는 `debug.log`를 수집한다. 모바일만 사용하는 기간에는 실제 게임 실행·실충돌 검증이 불가능할 수 있으므로 그 상태를 `미검증`으로 남긴다.

**모바일 사용자가 해야 할 수동 작업을 최소화한다.** 가능하면 설정값은 디버그 기본 ON으로 제공하고, JVM 인수·런처의 고급 설정 편집은 선택 사항으로 만든다.

### 6.3 재빌드 횟수를 줄이는 설계

- **컴파일을 다시 해야 하는 설정**과 **설정 파일·JVM 옵션만으로 변경할 수 있는 설정**을 분리한다.
- 경미한 진단 출력량·주기·대상 필터는 가능하다면 `config` 파일에서 조절할 수 있게 설계한다. 다만 설정 파일 시스템이 실제로 구현되지 않았다면 구현된 것처럼 적지 않는다.
- 기본 ON 테스트 버전에서는 최초 테스트에 설정 편집이 **0회** 필요하도록 구성한다.
- 로그 한 번으로 최대한 많은 판단을 할 수 있게 핵심 상태값을 정리하되, 콜백 내부 대량 I/O는 피한다.
- 변경할 때마다 모바일에서 여러 소스 파일을 직접 고치게 하지 말고, **완성된 새 소스 ZIP 1개**를 제공한다.
- 동일 원인의 컴파일 오류가 여러 파일에 퍼져 있으면 ZIP을 다시 만들기 전에 함께 수정한다.
- 빌드 실패 시 사용자가 전송하기 쉬운 **GitHub Actions 실패 작업명, 첫 오류와 인접 로그, 실행 커밋**을 우선 요청한다. 이미 제공된 로그는 다시 요구하지 않는다.

## 7. 오류 보고와 피드백 형식

각 개발 ZIP과 함께 아래 항목을 간단한 문서로 제공한다.

```text
[버전 / 기준 커밋]
[목표] 이번 ZIP으로 검증하려는 동작
[기본 활성화] ON 항목 및 이유
[비활성화/미구현] 항목 및 단계상 근거
[실제 관측 범위] 어떤 충돌이 로그로 잡히는지
[검증됨] 직접 실행한 검사와 결과
[미검증] Gradle/NeoForge/Mixin/실게임 중 검증하지 못한 항목
[모바일 적용] ZIP 업로드 위치 → Apply → Build → Artifacts
[테스트 방법] 게임에서 할 행동과 찾을 로그 태그
[실패 시 제출] 필요한 로그와 재현 조건
[이슈 추적] Issue 번호별 구현·미완료·검증 상태
```

**금지 표현:** `구현 완료`, `충돌 콜백 확인 완료`, `이슈 전부 충족`, `실행 가능 보장` 등 증거 없는 완료 선언.

**권장 상태 구분:** `구현됨 / 정적 검사 통과 / Gradle 빌드 통과 / 실제 게임 확인 / 미확정 / 미구현`.

## 8. 개발 산출물 릴리스 직전 체크리스트

### A. 핵심 목적

- [ ] 이번 버전의 핵심 목적을 한 문장으로 명시했다.
- [ ] 사용자가 요구한 기능이 **기본 ON**인지 확인했다.
- [ ] 핵심 기능을 끄는 플래그가 소스 다른 곳에 숨어 있지 않다.
- [ ] 핵심 경로가 런타임에서 실제 호출되는지 검증했거나 **명확히 미검증**으로 표기했다.
- [ ] 단계 외 기능을 비활성화한 이유가 사용자 요구/설계와 일치한다.

### B. 기술 검증

- [ ] 최신 설계와 최신 GitHub 소스/이슈를 기준으로 했다.
- [ ] 대상 Sable·Aeronautics·Create 버전과 시그니처를 검토했다.
- [ ] Mixin 설정 등록·대상·주입 실패 처리 정책을 검토했다.
- [ ] 일반 블록·콜백 미지정 블록을 포함한 **Sable 충돌 공통 경로 → PDD → 로그**를 점검했다.
- [ ] 목적-경로 추적표의 핵심 사례가 실제 계측 코드로 연결되었고, 전용 콜백만 구현한 것을 전체 연동으로 오판하지 않았다.
- [ ] 실제 충돌 테스트가 불가능한 경우 그 한계를 명시하고, 연동 완료 판정을 보류했다.
- [ ] 콜백 → 큐 → 서버 틱 → 로그의 전체 데이터 경로를 점검했다.
- [ ] 기존 Sable 콜백 결과·물리 충돌 반응을 보존한다.
- [ ] 실측 로그와 인공 진단 출력이 구분된다.
- [ ] 처리 한도·로그 제한이 데이터를 조용히 잃게 하지 않고 누락 건수를 보고한다.
- [ ] 미실행 테스트를 성공으로 기록하지 않는다.

### C. 모바일·배포

- [ ] 소스 ZIP 하나로 Apply Action을 진행할 수 있다.
- [ ] ZIP 구조를 현재 Apply Action 코드에 맞춰 검증했다.
- [ ] ZIP 내용과 압축 무결성을 확인했다.
- [ ] GitHub 워크플로·Gradle wrapper 보존 여부를 확인했다.
- [ ] JVM 추가 인수나 모바일 소스 직접 수정 없이 **최초 테스트를 시작**할 수 있다.
- [ ] Build Action과 JAR Artifact 획득 방법이 명시되어 있다.
- [ ] GitHub 이슈별 구현/검증 상태를 추적할 수 있다.
- [ ] 실제 수행한 검증과 미검증 항목을 별도로 적었다.

**릴리스 판정:** 핵심 목적이 기본 OFF이거나, **일반 블록을 포함한 필수 Sable → PDD 충돌 수집 경로가 빠졌거나**, 적용 가능한 ZIP 구조가 확인되지 않았으면 **배포 전 수정**한다. 기술적 한계로 기능이 미완성이라면 숨기지 않고 미완성 진단 버전으로 표시한다.

## 9. PDD 0.2.1 충돌 관측 기능의 점검 예시

아래 경로는 **당시 제공된 0.2.1-debug 소스 ZIP에 실제 존재하는 파일**이다. 향후 버전에서는 패키지/파일명이 달라질 수 있으므로 최신 소스를 확인한다.

| 소스 경로 | 확인해야 할 내용 |
|---|---|
| `src/main/java/com/physicaldestroydeform/diagnostics/SableContactQueue.java` | `ENABLED`의 기본값, 수집 건수, 큐 용량과 overflow 집계 |
| `src/main/java/com/physicaldestroydeform/mixin/SableCollisionBridgeMixin.java` | 주입 대상, `@Inject` 메서드, 콜백 입력 수집, 조기 반환 |
| `src/main/java/com/physicaldestroydeform/PhysicalDestroyDeform.java` | `debugCollisions`와 `onServerTick`의 조기 반환, `[PDD-COLLISION]` 출력 |
| `src/main/resources/pdd.mixins.json` | 주입 필수 여부·대상 등록·오류 처리 정책 |
| `src/main/resources/META-INF/neoforge.mods.toml` | Mixin 설정 참조 여부 |
| `docs/PDD-0.2.1-TEST-PLAN.md` | 기본 활성 상태와 게임 테스트 절차가 실제 소스와 일치하는지 |
| `expected-diagnostic-output.log` | 기본 설정과 예상 로그가 현재 빌드 설정을 반영하는지 |

**특별 주의:** 0.2.1의 목적 자체가 **Sable → PDD 충돌 데이터 전달 검증**이므로, `FragileBlockCallback`·`BeltBlockCallback`만 관측하는 구현은 필수 경로를 빠뜨린 것이다. 일반 블록 및 콜백이 없는 블록이 통과하는 공통 충돌 경로를 확인·계측하는 작업은 선택적 확장이 아니라 이 버전의 필수 구현이다. 해당 경로를 실제 바이너리로 확인하기 전에는 구체적인 주입 지점을 확정했다고 주장하지 않는다.
