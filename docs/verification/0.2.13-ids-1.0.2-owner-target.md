## 설계 불일치의 확인된 원인

1. 과거 `CollisionFrame.Snapshot.observe`의 `CONTACT_OUTSIDE_OWNER_BOUNDS` 검사에서 원시 접촉점의 블록 AABB 2블록 범위를 벗어나면 **양측 블록 타깃을 포함한 Evidence 전체를 `INVALID` 처리**했다. 실제 Sable 원시 인수의 placeholder 또는 다른 manifold 지점이면 소유자와 좌표를 버리게 된다.
2. 과거 `ContactPairMatcher`는 0.25블록 거리 비교로 두 콜백을 동일 접촉으로 승격했다. 서로 다른 다중 접촉점을 구별할 실제 manifold ID가 없는 상황에서 임계값만으로 승격할 근거가 없다.
3. 과거 `Snapshot.resolve`는 Plot의 넓은 X/Z 후보 범위를 사용했지만, 확정된 Plot 소유자·실제 블록 존재 여부·블록 종류를 서버에서 검증하지 않았다.

## 변경된 소스 및 실제 경로

- `collision/CollisionFrame.java`: Plot 식별 후보와 handle/pose 유효성을 분리. `BlockTarget`은 월드·Plot 각각 고유 `BlockPos`를 유지. 원시 기하값의 NaN/프레임 가설/블록 경계 바깥 결과는 **geometry** 상태만 무효/진단으로 기록하고, 블록 좌표 후보를 보존. 확인되지 않은 월드 접촉점은 에너지/손상 입력으로 승격하지 않는다.
- `collision/OwnerResolver.java` (신규): 서버 틱에서 `ServerSubLevelContainer.getPlot(ChunkPos)` / `getSubLevel(UUID)` / `ServerSubLevel.getUniqueId()` / Plot `EmbeddedPlotLevelAccessor.getBlockState(BlockPos)` 또는 `ServerLevel.getBlockState(BlockPos)`로 소유 공간과 실제 블록을 대조한다. **중요:** `EmbeddedPlotLevelAccessor`는 내부에서 `getCenterBlock()`을 더하므로, Sable 콜백의 절대 Plot 격자 좌표를 전달하기 전에 `allocatedBlockPos - plot.getCenterBlock()`으로 변환하고, `hasChunk`에도 `allocatedChunk - plot.getCenterChunk()`를 전달한다. 실제 Sable JAR의 `javap -c`로 이를 확인했다. 실재 블록의 ID/상태를 `TargetKey(dimension, space, plotId, own BlockPos, fingerprint)`로 반환한다. `BlockTarget`의 X/Z 판정은 **후보**, Sable 컨테이너+실제 블록 대조는 **검증**이다. 미확정·청크 부재·상태 불일치·스텝 지연 시 임의로 월드/다른 Plot으로 대체하지 않는다. 서버 틱 안에서만 결과를 캐시한다.
- `collision/ContactPairMatcher.java`: 동일 step·dimension·양방향 owner-local 블록 좌표로 **유일한 역방향 조합만** 상관관계를 확인. 한 프레임에 같은 소유자 쌍의 콜백이 여러 개면 `PAIR_AMBIGUOUS`; 좌표 0.25블록을 일치 인정값/타깃 조건으로 사용하지 않는다. 원시 접촉점 차이는 별도 진단 수치이다.
- `PhysicalDestroyDeform.java`: 서버의 실제 소유 타깃 성공/실패·Plot A↔Plot B·geometry 품질·다중 접점 모호성을 분리 집계하고, 원본 결과 보존·상대 타깃 검증 이유·원시 인수를 로그에 남긴다. 손상/변형/파괴 기능은 **0.2.13에서 비활성**.
- `diagnostics/RawObservation.java` 및 `ObservingCollisionCallback.java`: 단순 reciprocal/좌표 추론만으로 확정 frame이라고 주장하지 않도록 수정.
- `collision/CollisionFrameTest.java`, `ContactPairMatcherTest.java`, 신규 `OwnerResolverTest.java`: 서로 다른 Plot 식별, 경계 밖·NaN 기하에서도 소유자 보존, 정지 handle 부재, 중심-상대 Plot accessor 좌표, 다중 접촉, 0.25 초과 시 유효 타깃 미삭제, 미확정 fingerprint의 mutation 키 금지를 점검.

## API 및 런타임 진입점 근거

- 직접 확인한 업로드된 Sable 2.0.6 JAR 및 Jar-in-Jar `sable_rapier`의 `javap`: `BlockSubLevelCollisionCallback` 두 메서드, `RapierVoxelColliderBakery.buildPhysicsDataForBlock` → `BlockWithSubLevelCollisionCallback.sable$getCallback` → `Rapier3D.createVoxelColliderEntry` 경로 존재. 콜백 인수 **자체에는 owner enum·plot ID·manifold ID가 없다**. 바이트코드 시그니처만으로 원시 `impactPosition`의 모든 frame을 확정하지 않는다.
- Sable API `SubLevelContainer.getContainer(ServerLevel)` 및 `getPlot(ChunkPos)`, `getSubLevel(UUID)`, `LevelPlot.getEmbeddedLevelAccessor()`, `ServerSubLevel.getUniqueId()` 및 `isRemoved()` 존재; `EmbeddedPlotLevelAccessor`가 `BlockState getBlockState(BlockPos)`, `boolean hasChunk(int,int)`를 제공함을 `javap`로 확인.
- Sable Collision Damage, Sable Impact, True Impact의 owner-local 블록 접근 및 필요한 시점 변환/큐 분리를 **설계 참고**로만 사용. 외부 애드온의 라이선스 소스나 임의 피해 공식은 이식하지 않았다.
- `ServerTickEvent.Post.getServer()`는 NeoForge 1.21.1 Javadoc에서 공개 API로 확인. **공식 `compileClasspath` 기반 컴파일까지 성공했다고 주장하지 않는다.**

## 인게임 시험(최대 2회, 현재 ZIP 적용 후)

**시험 1 (한 세션)**: 정지·끼인 Plot → 잔디 정적 지형 충돌 → 돌벽 → **다른 Plot의 컨베이어벨트 구조물** → 돌벽 재충돌. 로그는 `[PDD-G-COL-02] phase=SUMMARY`와 `[PDD-G-COL-02] dimension=...`를 사용한다. 기대: `targetVerifiedBoth` 증가, 정적↔Plot `verifiedWorldPlot` 증가, 서로 다른 Plot `verifiedPlotPlot` 증가. 샘플 `hitTargetKey`와 `otherTargetKey`의 공간/plot ID/블록 좌표가 실제 건축물과 일치한다. 지형 좌표와 Plot 좌표가 같은 XYZ일 필요는 없다. `geometryQuality=DIAGNOSTIC_ONLY`라도 정확한 타깃은 유지하고 블록 변경 0.

**시험 2 (첫 시험에서 미확인 시에만)**: 서로 다른 두 Plot을 상대 회전한 상태에서 여러 블록이 동시에 닿도록 충돌. 기대: `stablePlotId`가 서로 다르고 각 Plot의 블록 좌표가 게임 내 블록을 가리킴. 중복 후보는 `pairAmbiguous` 증가 가능하며, 이를 타깃 소유자 실패로 간주하지 않음. 회전된 pose가 기하 품질과 별도로 기록됨.

**실패/보류 기준:** `targetVerifiedBoth`가 대표 충돌에서도 계속 0, 실제 소유자와 다른 Plot/월드가 선택됨, `OWNER_CHANGED`/`BLOCK_MISMATCH`가 정상 사례에서도 계속 발생, 원본 Belt/TNT/Fragile 동작 변화, 서버 충돌/틱 예외, JNI callback 반환값 불변 위반이면 실패. 모든 정상 사례의 geometry source/frame 검증이 없으면 게이트 `BLOCKED`. `targetVerifiedBoth=0`을 단순히 0.25 오차로 해결했다고 판정하지 않는다.
