- 설계 근거: `docs/PDD-1.0.7-Integrated-Design-Specification.md` §24.3·§31, 0.5.0 착수 설계 보완안

## 1. 보존한 0.4.1 실행 경계

`Collision/Credit → F-first 70:30 → sealed Q → WorldIntentMapper → WorldCommitCore → CAS/보호 이벤트 → PREPARED fsync → Vanilla break → 실제 블록 재조회 → terminal Receipt`.

`collision/ForcePropagation`, `ContactCreditLedger`, `WorldIntentMapper`, `NeoForgeWorldGateway`의 충돌 산출·F/Q 규약을 다시 구현하지 않았다. 실제 World 변경은 이전과 동일하게 서버 틱·로드된 청크·Vanilla `destroyBlock` 경유이며, Plot 실제 커밋은 비활성 상태를 보존한다.

`WorldCommitCore`의 기존 공개 생성자에 사용되던 `WorldReceiptJournal`은 이제 `WorldJournal`을 구현한다. 기존 schema 2 리더와 기존 테스트를 삭제하지 않았다. 새 `WorldPersistentJournal`이 동일 `WorldJournal` 계약을 구현한다.

## 2. 영속 파일 구조와 내구성 경계

```
<world>/data/pdd-world-0.4.1.wal       # 원본 schema 2: 이전 월드면 읽기 전용 보존
<world>/data/pdd-world-0.5.0/
  checkpoint.manifest                 # schema 1, CRC32, 세대, snapshot 참조 목록, legacy SHA-256
  recovery-N.wal                      # schema 1, ApplyId+Damage 원자 레코드, fsync
  chunks/<dimension-sha256-prefix>/<cx>_<cz>.<generation>.pds
  receipts/<sha256(ApplyId) bucket>.<generation>.pdr
```

- `WorldReceiptJournal`의 0.4.1 schema 2 데이터를 엄격한 CRC·범위 검증 후 Snapshot/Receipt로 마이그레이션한다. 기존 `.wal`은 수정·삭제하지 않는다.
- 모든 운영 파일은 magic/schema/type/길이/CRC 검증. Snapshot은 immutable generation별로 작성, 체크포인트 Manifest만 원자적으로 교체한다.
- **내구성 순서:** WAL 프레임(fsync 완료) → 메모리 게시, PREPARED 선행 fsync → 실제 블록 변경 → 블록 재조회 → APPLIED/QUARANTINED 선행 fsync.
- 교체 tombstone과 incarnation revision은 단일 WAL 프레임으로 저장한다. PDD 자신의 블록 파괴도 완료 후 revision을 영속 갱신해 동일 블록 재설치 시 기존 큐가 오인 적용되지 않게 한다.
- Checkpoint는 기존 WAL을 유지한 채 변경된 청크/Receipt 버킷만 새 세대로 기록한다. 새 빈 WAL과 immutable Snapshot을 fsync한 뒤 Manifest를 원자 교체한다. Manifest 확정 후에만 이전 파일을 정리한다.
- Manifest 미확정 상태에서 종료되면 이전 Manifest + WAL로 복원한다. 마지막 WAL의 미완성 추가 프레임만 안전 경계상 제거하고 `repairedTailBytes`로 진단한다. 완성 프레임의 CRC 오류, 스키마 오류, Snapshot 손상은 **fail-closed**다.
- 이전 0.4.1을 실행해 원본 WAL이 바뀌거나 0.5.0 신규 월드에 나중에 이전 WAL이 생성되면, 재시작 시 분기 위험을 탐지하고 커밋을 중지한다.

## 3. 메모리·디스크·백프레셔 정책

| 정책 | 기본값 / 판정 |
|---|---|
| 손상 상태 | `damageU8`, `remainderU8`, 0인 상태 저장 안 함 |
| 청크별 손상 키 | 최대 4,096개 (4097번째는 `SPARSE_CHUNK_CAP_EXCEEDED`) |
| 전체 활성 손상 키 | 2,000,000개, 메모리 보호용 상한 |
| Receipt 원장 | 2,000,000개, **임의 폐기 없음**. 60,000개 기존 상한을 버킷 Snapshot으로 대체 |
| incarnation revision | 전체 4,000,000개 / 청크 131,072개, 세대 재사용 방지 |
| Recovery WAL | 최대 96 MiB, 16 MiB 이후 조기 체크포인트 |
| dirty flush | 최대 128개 Snapshot 객체/호출, 약 2ms 소프트 시간 예산(개별 fsync 초과 가능) |
| Checkpoint | 100틱마다 또는 WAL/Dirty 압력 발생 시, 작업 중이면 다음 틱 계속 |
| World 큐·파괴 제한 | 기존 16,384개 큐 / 1,200틱 TTL / 기본 64블록/틱 보존 |
| 파일 오류·상한 | 성공으로 위장하지 않고 신규 World 커밋 중단·거절 사유 로그. Credit 재발급 없음 |

Receipt를 지우지 않고 중복 방지를 유지한다. 2백만 개 상한에 도달하면 fail-closed로 신규 커밋을 제한하며, 오래된 ApplyId를 안전하게 폐기할 수 있는 **별도 증명된 TTL/epoch 재발행 계약**이 없는 이상 ID를 무단 삭제하지 않는다. 따라서 장기간 무제한 저장이 가능한 것은 아니다.

## 4. 복원/검증 원칙과 한계

- 월드 청크를 강제로 로드하지 않는다. Disk Snapshot을 읽었다는 이유만으로 실제 월드 블록 검증에 합격한 것으로 처리하지 않는다.
- 새 충돌에는 `dimension + ownerGeneration + fingerprint + durable incarnation`으로 CAS 확인을 수행하며, 같은 셀에 다른 fingerprint로 이미 저장된 손상이 있으면 `STALE_POSITION_STATE_QUARANTINED`로 처리한다.
- 재료 세대값 변경은 과거 damage/remainder를 소급 재계산하거나 무단 초기화하는 근거가 아니다.
- 충돌 당시 Plot UUID·소유자·좌표는 기존 구분 유지. 0.5.0은 **World만** 저장·변경하고 Plot 실제 피해/분리 이전은 후속 버전이다.
- 원본 0.4.1에서 이미 관측되지 않은 교체 사건/월드가 꺼져 있는 동안 이루어진 동일 상태 재설치는 사후에 정확히 복원할 정보가 없다. 0.5.0은 관측 가능한 server-thread 교체에 대해서만 durable incarnation을 보장한다. 외부 도구가 월드 파일을 직접 고친 경우 별도 검사·격리가 필요하며, 모든 상황의 물리적 정확히 1회 드롭을 보증하는 것은 아니다.
- 서버 시작 시 Snapshot은 차원·청크 단위 파일별 검증을 수행하나 인메모리 색인은 **선행 복원**한다. 실제 월드 데이터 조회는 청크가 이미 로드된 경우에만 수행한다. 대규모 저장소에서 인덱스 자체까지 지연 로드하는 기능은 이 코드에 구현돼 있지 않다.

## 6. 정적·독립 검증 (실제 CI/JUnit과 분리)

- 임시 JUnit 호환 Assertion/Annotation 스텁을 이용한 **독립 테스트 하네스**: 신규 `@Test` 20건 실행, 20건 성공. **정식 JUnit Jupiter 런너 실행 결과가 아님.**
- 기존 `WorldCommitCoreSelfTest` 독립 컴파일·실행: 44개 자기검사 성공.
- 확인한 시나리오: schema2 마이그레이션, legacy WAL CRC/쓰기 분기, 분산 차원·청크 저장, 미확정 PREPARED·DEFERRED, ApplyId 재실행 차단, 4096한계, 60001 Receipt, 손상/나머지/물성 세대, 동일 상태 교체, 스냅샷·Manifest·WAL CRC 손상, 체크포인트 중도 종료, WAL torn tail, 저장 실패, unloaded chunk, 보호 거절, PREPARED 선행 fsync.

- GitHub Actions Build/Callback Test: 이 버전 적용 후 **미실행**; 기존 0.4.1 baseline의 Build 성공 사실과 분리.
- 실제 Minecraft 인게임: **미실행**, 사용자 테스트 필요.

## 7. 인게임 로그 / 검증 절차

JVM 플래그 `-Dpdd.persistence.verbose=true` 또는 `-Dpdd.world.verbose=true`를 사용하면 손상 큐·변경·체크포인트의 상세 로그가 활성화된다. 기본 상태에서도 START, SUMMARY, 결과의 앞 20건/틱, 오류·격리는 기록된다.

식별용 Prefix: `[PDD-PERSIST] phase=START|CHECKPOINT|RECOVERY_TAIL_REPAIR|REPLACEMENT|STORAGE|STOP_CHECKPOINT`, `[PDD-COMMIT] phase=QUEUE|OFFER|RESULT`, `[PDD-SAVE] phase=RECONCILE|SUMMARY|HALTED`. 각 RESULT의 `id`, `key`, `damageU8`, `remainderU8`, `receiptStatus`, `walBytes`로 저장과 실제 피해 연결 여부를 추적한다. 로그 예제는 실제 관측 결과가 아니고 **예상 형식**이다.

### 최대 두 번 실행하여 확인

1. **첫 실행**: 테스트 월드 백업 후 PDD 0.5.0을 적용, 호환 모드(Sable/Create/Aeronautics)로 서버 시작. `phase=START`에서 legacyMigration, restoredDamage/Receipts, storage schema 확인. 평범한 World 블록(예: 돌)에 짧은 충돌을 여러 번 발생시켜 `APPLIED_DAMAGE`(손상·나머지 증가), 강한 충돌로 `PREPARED_DURABLE → APPLIED_BREAK`, World 변경/드롭 1회 확인. 테스트용 블록 한 개는 미완성 손상 상태로 남기고 정상 종료(`STOP_CHECKPOINT`)한다.
2. **둘째 실행**: 같은 월드 재시작. START에서 storedDamage/Receipts가 보존되었는지 확인. 이전 ApplyId가 중복 적용되지 않는지 로그와 실제 드롭 수 확인. 손상 블록을 채굴했다가 동일 블록을 재설치해 `phase=REPLACEMENT incarnationRevision=... damageInvalidated=true`를 확인. 이전 손상이 새 블록에 복제되지 않고 새로운 충돌에서만 누적되는지 관찰. 가능하면 청크 언로드/재로드 후 동일 블록 확인.

오류 시 제출: 두 실행의 `latest.log` 및 `debug.log`(충돌 직전 20초~재시작 직후), `PDD-SAVE`, `PDD-PERSIST`, `PDD-COMMIT`, `PDD-OBS` 행, Actions JUnit 실패 스택, 테스트 월드의 `data/pdd-world-0.4.1.wal`과 `data/pdd-world-0.5.0/` **전체 복사본**. 가능하면 기존 데이터 파일은 백업한 후 보관하고 직접 수정을 금지한다.

## 8. GitHub Apply 계약

`Apply PDD ZIP`은 ZIP 안에서 Gradle 루트를 탐지해 기존 repo의 비보호 파일을 동기화한다. `.git`, `.github`, `incoming`, `gradlew`, `gradlew.bat`, `gradle`은 GitHub 워크플로에서 **보호**된다. 이 ZIP에는 기존 `FULL-SOURCE-APPLY`의 비보호 소스·리소스·테스트·설정·문서를 모두 보존한다. GitHub의 보호 Wrapper·Actions 파일을 임의 교체하지 않고 **기존 GitHub main**을 그대로 사용한다. `incoming/`에는 정확히 하나의 ZIP만 올려서 Apply가 원치 않은 파일을 삭제하지 않게 한다.
