## 2. Implemented requirements

### Material registry and H/T/D/E

- `MaterialProperties` now holds `H[0..255]`, `T[1..255]`, `D[0..100]`, `E[0..100]`, an independent `unbreakable` policy and finite nonnegative `yieldThreshold`. The historical 3-argument constructor remains valid.
- `MaterialRegistry` builds block-definition profiles at server startup/datapack sync; the immutable `Snapshot` atomically carries `materialGeneration`, definition values and owner-neutral relevant BlockState variations. No per-position recipe scans occur in the impact hot path.
- `HardnessScale` uses `ln(1+s)/ln(56)` and `ln(1+b)/ln(1201)`, with `0.60/0.35/0.05` policy weights and no unverified tool-tier evidence (`R=0`). `T_base=round(1+254*(H/255)^0.65)` is independent of the final H after explicit override.
- Existing sorted recipe inspection blends H/T/D/E as **gameplay inference**, not real ingredient mass. Deterministic first supported recipe by ID; unsupported entries fall back to the registered definition. Explicit exact vanilla profiles are applied afterward, then the user's `pdd-materials.json` override. See `pdd-materials.example.json` for optional exact block-state selectors such as `axis=x`. Neither uncertain mod IDs nor ID substrings are assigned authoritative metal properties.
- Explicit anchors: reinforced deepslate `H=255,T=255`; obsidian `D=0,E=0`; slime `E=100`; gold `D=100`. Other vanilla defaults are provisional tuning profiles. Naturally unbreakable blocks retain their veto even if their numerical H is 255.

### Per-credit material planning

- After the **existing** R2-verification + `GameImpactCredit` + `ContactCreditLedger.issue` path grants the first authorised event, `MaterialPlanner.plan` reads only already-issued target `Share.q()` and a single immutable material-generation snapshot. It never creates a new collision credit or changes the original Sable callback.
- Per-target Q and damage formula from §24.1:

```
e=E/100
fE=0.15 + 0.85 * (1-e)^1.5
active=Q_target * fE
absorbed=Q_target-active
direct=active*0.60
plastic=active*0.15
stress=active-direct-plastic
fH=0.08 + 0.92 * (1-H/255)^1.5
rawDamage=direct*fH   # provisional damageGain 1.0
incrementFixed=floor(max(0,rawDamage)*256)
nextFixed=min(65535,oldDamage*256+oldRemainder+incrementFixed)
```

- `plastic` and `stress` are **UNUSED_PLANNED** in 0.4.0. They are *not* reassigned to direct damage. `plannedPlasticIncrement` is a diagnostic candidate bounded by `D` capacity and yield, **not applied deformation**. A threshold-crossing preview is not a world `DestroyIntent`.
- Validation rejects negative/NaN/∞ source Q and invalid settings. Both H and E have nonzero minimum transmission by design. Incomplete/unknown material target Q is not reallocated to other targets. `ContactCreditLedger.Grant.spent()` remains zero because there is no commit.
- `BlockDamageState` stores independent damage/deformation/crack bytes **plus one separate remainder byte**. Subunit impacts use floor-to-fixed increment; the old prototype `ceil` behavior has been removed. All values saturate to unsigned 8-bit bounds.
- `DirectionEvidence` provides an optional verified owner-frame, normal source, source quality, source tick/substep, transform epoch and signed axis. No 0.3.1 native direction is promoted to verified; in 0.4.0 all live plans have direction UNKNOWN.

### Sparse state base / serialization

- `SparseStateKey`: dimension, `WORLD` or `PLOT` stable owner identity, owner generation, owner-local XYZ and original verified block fingerprint. Runtime body ID and Java `hashCode()` are not storage identifiers.
- `SparseDamageState`: 3 independent u8 fields, independent 1-byte fixed remainder, material generation and update tick. Zero-state keys are invalid.
- `SparseStateCodec` schema v1: canonical sorted binary entries, CRC32, magic+version, 65,536-record/16 MiB decode caps, length/range/duplicate checks and fail-closed errors. These are **pure serializer** tests: the game does not load/write the file or treat decoded bytes as safe for a live block in 0.4.0. Live owner, epoch, fingerprint and loaded-chunk validation become mandatory at 0.4.1.

## 3. Compatibility and safety

- Unmodified `RealFixRuntimeBridge` core owner/generation/coordinates, Sable original post-effect reader, `GameImpactCredit` four-phase FSM, world two-proof rearm, R2 32 checks per side, 8192-cell world-clearance bound, region ledger and 64-Q cap. Existing Q calibration remains `forceGain=0.001` unless explicitly changed by the existing `pdd.realfix.forceGain` property.
- The runtime material code is guarded after a credited `Grant`; exceptions result in `[PDD-MATERIAL-PLAN] reason=PLAN_REJECTED` and **no block mutation or replacement Q**. No new Sable API calls or JNI ABI.
- `[PDD-MATERIAL-PLAN]` summarizes revision, generation, target count, missing material, Q accounting and aggregate fixed-point increment; `[PDD-MATERIAL-TARGET]` samples up to 8 genuine owner-local targets with H/T/D/E, elastic, Direct/Plastic/Stress, raw/fixed values and `applied=false`. Each 100-tick summary also reports planned/rejected counters. Historical `[PDD-EPISODE]`, `[PDD-LEDGER]`, `[PDD-VERF-FSM]` and original callback diagnostics remain.

## 7. Remaining risks (not 0.4.0 feature omissions)

- Native 100-record limit and R2 per-side 32-cell limit remain as measured upstream/safety constraints; a 0.4 material plan cannot invent missing collision data.
- Q remains a provisional gameplay force proxy, not solver impulse or physical Joules. The initial material profiles and yield are game calibration, not empirical metallurgy.
- Receipt/ApplyId durable commit, safe World break/drop, restart recovery, full chunk sparse save, Plot split transfer, stress graph, actual deformation, visuals and external source integration are explicitly assigned to 0.4.1–0.8.1 by IDS 1.0.6. They are **not** simulated as completed functionality in this release.
